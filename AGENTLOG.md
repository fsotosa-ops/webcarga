### 2026-07-25/26 — Ronda 45: incidente real — viajes sin aparecer desde el 22, Tarifario "se ve como data cruda", deuda de locations

**Contexto**: el usuario reportó 3 cosas en la misma sesión: (1) los viajes de hoy no aparecen desde el miércoles pasado, (2) el Tarifario se ve desconectado del resto de la app, (3) las locations no están alineadas con `public.locations`. Investigado contra datos reales (Supabase MCP + sync del proyecto Mage real) antes de tocar nada.

**Incidente 1 — resuelto**: `app.trips` tenía 0 filas nuevas desde 2026-07-22. Root cause confirmado con datos, no hipótesis: `bronze.tms_trips` mostraba qanalytics/sodimac frescos al día pero `wingsuite` parado en 2026-07-21 23:48. El pipeline `batch_tms_monitor_trips` converge las 3 fuentes en un único bloque compartido (`tms_trips_snapshot`) que exige que las 3 terminen — una sola fuente rota bloqueaba el pipeline completo para todas. El usuario confirmó en vivo que `processor_wingsuite_files` era el bloque que fallaba.

Cadena de bugs reales encontrados y corregidos, uno a uno, cada uno expuesto recién al arreglar el anterior (nunca antes se había llegado tan lejos en este código con un batch de wingsuite parcialmente vacío):
1. `data_loaders/processor_wingsuite_files.py`: `pd.concat(lista_dfs)` con `lista_dfs` vacía (archivos nuevos encontrados pero todos vinieron vacíos vía `EmptyDataError`) tiraba `ValueError: No objects to concatenate`. Fix: devolver `pd.DataFrame()` si `lista_dfs` queda vacía, mismo criterio que el early-return ya existente para "no hay archivos nuevos".
2. `custom/wingsuite_payload_transformer.py` (función `transform_custom` y su `@test test_output`): `data.empty`/`output.empty` tiraban `AttributeError: 'DataFrame' object has no attribute 'empty'` — el DataFrame vacío que cruza el boundary entre bloques de Mage en este entorno no se reconstruye como un `pandas.DataFrame` completo (causa exacta no confirmada — posible artefacto de serialización), pero `len()` sí funciona igual. Mismo patrón (`.empty` sobre un parámetro recibido cross-block) existe también en `qanalytics_agg_nro_sap_transformer.py`, `qanalytics_agg_iansa_transformer.py` y `sodimac_payload_transformer.py` — **no tocados**, siguen funcionando hoy, dejarlo así salvo que se rompan.
3. `data_exporters/ingestion_tmp_raw_wingsuite_trips.py`: con un batch vacío, el bloque no creaba `bronze.tmp_raw_wingsuite_trips` (tabla efímera, la crea este bloque y la dropea `insert_raw_tms_trips_wingsuite.sql` al final) — el bloque SQL siguiente fallaba con `UndefinedTable`. Fix: crear la tabla vacía con el esquema correcto en vez de saltarse el export.

Se intentó agregar un bloque `conditional` (`wingsuite_has_new_data`) para cortar la ejecución de la rama completa cuando no hay datos nuevos, en vez de seguir parchando bloque por bloque — creado pero **no se pudo conectar como upstream de `wingsuite_payload_transformer` vía la API del mage-agent** (el campo no persistía el cambio). A pedido del usuario, se abandonó ese enfoque y se volvió al parche bloque por bloque, que sí funcionó. El bloque `wingsuite_has_new_data` quedó creado en Mage pero **desconectado** (sin downstream) — no afecta ninguna corrida, pero conviene borrarlo a mano desde la UI de Mage (no hay tool de `block_delete` en el mage-agent).

**Verificado en Supabase tras el fix**: `app.trips` repobló 2026-07-22→2026-07-26 (40/44/47/39/3 filas respectivamente, en línea con el volumen histórico ~30-48/día). El síntoma reportado por el usuario está resuelto.
